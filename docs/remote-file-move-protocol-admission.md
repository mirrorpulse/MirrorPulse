# Remote file move protocol admission

Product catalog schema 66 can retain an immutable admission to the audited
`CfSharp.RemoteFileMove.v1` protocol. The record belongs to the original registered
file move, complete immutable batch reference and version 2 before-native start.
It retains the actual original official revision, selected SDK package and source
commit, original apply policy, and the Host's verified admission time. It does not
replace any original start, native binding, membership, or rejected history.

Before recording admission, the Host must freshly verify the original native
source, its official revision, current execution role, and both protected parents
under the shared namespace actor and native guards. The catalog checks the
original pending execution and excludes directory, ordinary local, unstarted,
legacy-start and already observed or settled moves. Reopening the catalog
validates the payload digest, canonical representation, complete original intent
fingerprint and unchanged start. Replaying an admission returns its original
history; another source commit or apply policy cannot replace it.

The retained policy includes preservation of unsynchronized local content, echo
suppression, echo lifetime and observation count. It excludes `MaximumEntries`,
which can change during immutable-batch replay under the SDK contract. A new
library version requires an explicit compatibility review before it can create
this admission; a version string alone does not establish native recovery.

This record is a product admission, not evidence that an SDK preparation, native
rename, item projection or batch outcome committed. The SDK must authenticate its
own retained preparation through its supported original-batch API. Applications
do not decode SDK recovery checkpoints or infer successful movement from this
record. Only the actual public entry/progress and subsequent protected target
verification can authorize product settlement and the Adapter cursor.

Upgrading a schema 65 catalog creates no admissions for historical moves. An
existing start cannot acquire historical SDK proof merely because its object is
now at the target. A source that is freshly proven unchanged can be admitted to a
supported protocol before its first dispatch under that protocol. The original
start still remains immutable. Foreign keys and the product schema fence prevent
older Hosts from silently ignoring these new facts.

The preview.6 runtime records this admission under its fresh before-dispatch
guards and uses it to select original-batch file recovery. Missing admission
retains the existing unmoved-source route; a moved target cannot invent one.
Native acceptance of the revised production-driver fixtures is still required
before automatic recovery can be claimed. Directory movement, execution-role
handoff and default Host composition retain their separate requirements.
